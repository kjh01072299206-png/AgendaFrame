# 스테이징·카나리·모니터링·롤백 운영

## 단계

1. **검증**: 오프라인 quick/full 게이트, 릴리스 게이트, 의미 검토표를 통과합니다.
2. **스테이징**: 실제 사용자에게 공개하지 않는 별도 배포에서 health, API 계약, 커뮤니티 신고, 챗봇 근거 연결을 확인합니다.
3. **카나리**: `site/config/release-gate.json`의 초기 트래픽 비율과 관찰 시간을 적용합니다. 카나리 버전은 immutable build ID로 기록합니다.
4. **승격 또는 롤백**: `release-guard.mjs`의 출시 게이트와 SLO 결과를 함께 평가합니다. 둘 중 하나라도 실패하면 이전 immutable 버전을 선택합니다.

## 최소 모니터링 항목

- API 오류율과 p95 지연
- 이슈 상세·근거 API의 5xx 비율
- 근거 없는 챗봇 답변 및 보류 비율
- 커뮤니티 신고 큐의 개수와 가장 오래된 대기 시간
- 수집·분석 데이터의 기준일과 stale 상태
- 출시 버전, 모델/프롬프트/코드 버전

## 자동 롤백 경계

`release-guard.mjs`는 배포 공급자에 토큰을 보내지 않습니다. 입력된 출시 지표와 이전 버전 ID를 바탕으로 롤백 대상을 결정하는 순수 결정 로직입니다. 실제 Sites/Vercel/GCP 배포 API에 연결할 때는 staging 프로젝트, 예산 제한, 최소 권한 서비스 계정, 이전 버전 보존을 별도로 설정하고, 연결 후에만 자동 롤백을 운영 기능으로 표현합니다.

현재 저장소의 CI 릴리스 게이트는 실제 라벨이 없는 상태에서 실패하도록 의도되어 있습니다. 이는 synthetic fixture만으로 운영 배포되는 것을 막는 fail-closed 정책입니다.
